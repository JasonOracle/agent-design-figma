# D1 硬验收标准

> **这份文档治的是「承诺」与「验收」之间的落差。**
> `1.2-plan.md` §4-D 原本把 D1 写成三句话——「不手工修改 JSON / 不引用不存在的东西 / 不目测评分」。
> 那三条是**行为承诺**，而行为承诺无法验收：跑完之后产物上没有痕迹证明 Agent 当时守没守规矩。
> 1.1 的教训正是这个——上游把「检查文档引用」列成人工勾选项，勾了却没做干净（12 处失效引用），
> 于是 1.2 用 `check-refs.mjs` 把它变成机械闸门；安装提示语口说无凭，于是 1.2 用 `qa-install.mjs`
> 真跑探针、逐字复算。
>
> 所以 D1 的落地方式**不是**「写一句更严的承诺」，而是：**把三条挂到链路出口的机械闸门上，
> 每条给出确切命令、确切退出码、确切的失败归因**。判定由工具做，不由人做。

---

## 0. 三条标准 ↔ 机械裁判映射

| # | 标准（原文） | 真正的判据 | 裁判工具 | 不通过的样子 |
|---|---|---|---|---|
| **H1** | 零人工补丁 | 产物里每个数字**要么算得出、要么指得出源**；声明的能力不超过当时档位 | `qa-l2.mjs` / `contrast-audit.mjs` / `qa-critic.mjs` / `qa-export.mjs` | 出现一个「来源推不出来、又复算不上」的值 |
| **H2** | 零失效引用 | 文档引用 0 悬空；计划里的 op / 参数 / 画布 id 全部真实存在 | `check-refs.mjs` / `precheck.mjs`（离线 + `--live`） | 引用了不存在的工具 / 文件 / op / 画布节点 |
| **H3** | 零目测评分 | L4 每一维分数都有工具输出作证；未评估项不得当作通过 | `qa-critic.mjs` / `contrast-audit.mjs` | 某维分数只有形容词，没有量或核对动作 |

**共用的三条口径**（与 `precheck.mjs`、`qa-install.mjs` 一致，不要另立一套）：
1. **硬 / 软分档**：只有硬判据进退出码；软判据出 `WARN`，`--strict` 下才致命。
2. **三档归因**：结构错误（离线可判定，必定为真）｜契约错误（真源码裁决）｜**装置缺口**（桩没覆盖到，单列，**不算产品缺陷**）。
3. **算不出 ≠ 通过**：取值无法解析（非 `#RRGGBB`、缺字段）时，必须报「无法计算」并计入失败，不得静默放过。

## 1. 先定档，再验收

### 1.1 档位是验收的前提

「跑一次完整链路」在不同机器上能跑到的位置不同，D1 必须**先记录档位再判**，否则会出现
「在离线机器上声称画布已写入」这类自欺。档位由探针判定，不由人自述：

```bash
node tools/runtime-check.mjs
```

输出 `mode` ∈ `FULL_MODE` / `READ_ONLY_MODE` / `OFFLINE_MODE`（判据与能力矩阵见 `references/runtime-capability.md`）。

### 1.2 各档位下 D1 的可判范围

| 档位 | L3 能做什么 | L4 能否跑 | L5 形态 | D1 可判范围 |
|---|---|---|---|---|
| `FULL_MODE` | 真画上画布 + 回读 | 可跑（通用档 + 增益档） | `live-build` | **全量**（H1 / H2 / H3 三条都判） |
| `READ_ONLY_MODE` | 只产出构建计划，**不执行** | **不适用**（仅当用户提供既有 Figma 文件链接时允许只读审查，且不得谎称是「生成后审查」） | `design-phase` | H1 / H2 判；**H3 不适用**（没有 critic-report 可判） |
| `OFFLINE_MODE` | 只产出设计资产（Brief / DS Spec / Build Plan） | **不适用** | `design-phase` | 同上；且 L3 必须显式标「未执行」 |

> 这张表**照抄** `references/runtime-capability.md` §3 Capability Matrix 与 §4 逐层降级规则，不是本文件另立一套。
> 若两者不一致，以那份为准（它才是 Skill 消费的判定表）。**D1 不发明档位语义**——
> 例如「非 FULL_MODE 下 L4 也能出通用档证据」这种说法虽然听起来合理，但与 §4「L4 仅 FULL_MODE」冲突，故不采纳。

### 1.3 低档不得冒充高档（这是硬判据）

低档位下，产物**不得**出现下列声明：`liveBuild` 形态的导出清单、`nodeId` 已回读、
`figmaFileKey` 非 `null`、`exports` 指向画布节点；也不得声称「本次已对生成结果完成视觉评分」
（`runtime-capability.md` §4 只允许 `READ_ONLY_MODE` 在用户给出既有文件链接时做**只读审查**，
且必须如实标注为对既有页面的审查，不得说成「生成后审查」）。

- 已有守卫：`qa-export.mjs` QA2（`design-phase` 的规划路径必须带 `_meta` 说明）、
  QA3（`design-phase` 必须诚实标 `figmaFileKey=null`）、`SKILL.md` 的诚实铁律
  （未跑的层不得假装跑过 / 执行）。
- 归因：命中即 **H1 不通过**——这是「编了一个不是这次跑出来的事实」。

## 2. H1 · 零人工补丁

### 2.1 判据 A：每个数字要么算得出、要么指得出源

「手工补丁」的本质特征**不是**「手碰过文件」，而是**产物里出现了推不出来源的值**——
人写上去的、没经过公式或上游的。所以判据是「复算 + 回溯」，不是「检查有没有手改」。

| 复算什么 | 裁判 | 断言的边界 |
|---|---|---|
| 派生 token 色值 | `qa-l2.mjs` QA2 | 带 `derived:` 即强制按公式复算，**不得**用「值在色板内」蒙混 |
| `accessibility.contrast` 声称值 | `contrast-audit.mjs` | 逐条与 WCAG 复算比对；声称里的 hex 还须与 token 实际值一致；判定用**未舍入**原值 |
| 导出 `value` 快照 + `source` 继承 | `qa-export.mjs` QA5 | `value` 须与 DS Spec 原值**逐字相等**；`source` 须继承自 Spec 叶子 |
| `critic-report.average` | `qa-critic.mjs` QA3 | 由五维实算得出（half-up 一位小数），不得手写总分 |
| 证据 / 映射里引用的量 | `qa-critic.mjs` QA8、`qa-export.mjs` QA9 | 引用的 token 色值 / 标量 / 档位必须与 Spec 对得上；`preset:<id>.<路径>` 必须真的解析得到 |

**为什么这组判据可信**：它们不是为 D1 新写的，是 C1 / C3 的既有断言，而且**上线即抓到了东西**——
9 条被编造的对比度声称值、32 处与 Spec 对不上的产物值、17 条解析不到的假溯源。能抓到 = 有区分度。

### 2.2 判据 B：产物指得出上游，且上游真实存在

- `qa-critic.mjs` QA8：`_meta.inputs` 里形如路径的条目**必须存在**（产物是从那份上游产出的）。
- `qa-export.mjs` QA8：身份一致——`manifest.project` == `source.brief.product.name` == `source.dsSpec.brand.name`。
- `qa-export.mjs` QA9：可追溯性——溯源串必须能解析到真实路径，前缀合法 ≠ 路径真实存在。

### 2.3 判据 C：能力声明 ≤ 档位上限

见 §1.3。这一条与判据 A/B 一起，构成 H1 需要的全部机械证据。

### 2.4 已知盲区（如实列出）

D1 **没有**、也做不到「产物是否被人手工编辑过」的直接证据。判据 A/B/C 是**代理**：
一个值若既算得出、又指得出源、又不越档，那它与「机器生成」在可观测层面不可区分——
这正是验收能到达的边界。**不声称超过了这个边界。**

## 3. H2 · 零失效引用

失效引用发生在三个不同时刻，需要三个不同的裁判：

### 3.1 时刻一 · 写文档时（引用文件 / 工具）

```bash
node tools/check-refs.mjs
```

- **通过条件**：`0 悬空`（退出码 0）。
- 覆盖：全部随包发布的 `.md`，含命令式引用（`node` 后的脚本路径）与反引号内的带扩展名路径。
- 判据四条：仓库根存在 / 文档同级存在 / 全仓库同名 / glob 匹配——**四条都不中才算悬空**。
- 归因：命中即「文档承诺了不存在的东西」，改措辞或补文件，**不得放宽校验器**（这是本仓库已立的规矩）。

### 3.2 时刻二 · 发计划前，离线（引用 op / 参数）

```bash
node tools/precheck.mjs <build-plan.json>
```

- **输入**：你**正要发出去的那串 op**（不是 DS Spec 的 `buildPlan`——那个字段只有批次视图，没有 op 序列）。
- **契约的事实源**：真 `figma-plugin/code.js`（用 vm 离线跑，不是另抄一份形状表）。
- **通过条件**：退出码 0 = 无结构错误、无契约错误。可含**装置缺口**（桩没覆盖到，单列）与「待核对的外部引用」。
- **装置缺口不算产品缺陷**，但**必须记录**——它是本次验收没看到的盲区。
- 归因：退出码 1 = 计划里引用了 code.js 不认的 op / 参数形状错。修计划，不是修预检。

### 3.3 时刻三 · 发计划前，在线（引用画布已有节点）

```bash
node tools/precheck.mjs <build-plan.json> --live
```

- 只有 `FULL_MODE` 有意义（要连 Bridge + 插件）。逐个用 `get-node` 核对计划里引用的字面画布 id。
- **通过条件**：退出码 0 且**零意外响应**。出现超时 / 掉线 / 未领取时，预检**不得**声称「外部引用全部存在」——
  这是它已修的缺陷，别退回旧行为。
- 边界如实写：**这是核对，不是仿真**（Figma 无事务，做不到「先跑一遍再回滚」）。

### 3.4 无图环境怎么办：记「未核对」，不许记「通过」

`OFFLINE_MODE` / `READ_ONLY_MODE` 下 §3.3 跑不了。此时：

- 验收记录里该行填 **`未核对`**，并写明原因（无 Bridge / 探针报 OFFLINE）。
- **`未核对` 不等于通过，也不等于不通过**——它是这条判据在本次验收中**没有证据**。
- 连带效果：L5 必须是 `design-phase`，且 H1 判据 C 会约束产物不得声明画布已写入。
  **两个档位下的验收结论不同，如实写清楚是哪种，不要合并成一句「通过」。**

## 4. H3 · 零目测评分

> **前提**：L4 只在 `FULL_MODE` 跑（`references/runtime-capability.md` §4）。非 `FULL_MODE` 下
> 没有 `critic-report.json`，本节判据**不适用**——记「不适用」，**不适用 ≠ 通过**。
> 此时 L5 只能是 `design-phase`，H1 判据 C 会同时约束产物不得声称画布已写入。

### 4.1 判据：每维分数都有通用档证据

L4 出口逐份报告过闸：

```bash
node tools/qa-critic.mjs --report <critic-report.json> --brief <brief.json> --spec <dsspec.json>
```

| 断言 | 治的目测病 |
|---|---|
| QA4 | 每条 issue 的 `evidence` 必须带**量**或带**核对动作**——判**形状**，不是判关键词出现过（关键词袋曾放过「不够高级」，见 `references/lessons.md` #40） |
| QA6 | 有 `critical` issue 时**禁止 PASS**；`action` 与分数互推（挡住「问题一堆却判通过」） |
| QA7 | `_evidence.mode` 合法；`structured-only` 时 `visionObservations` 必须为空；**`structured-only` 时 `unassessed` 必须非空**——声称「零未评估项」等于把没看当看过 |
| QA8 | 证据里引用的量必须与 DS Spec 对得上（挡住「证据里写的数字是编的」） |

Color 维另加一道复算：

```bash
node tools/contrast-audit.mjs <dsspec.json>
```

### 4.2 权重处理（C2 §1.6，容易做错的一步）

通用档下无法评估的检查项，必须**剔除权重并对余项重新归一化**。

- 把「没看」按**满分**计入 = 放过缺陷；
- 把「没看」按**零分**计入 = 凭空扣分。

两者都是编。**只有重新归一化**才是当时能得到的诚实分数。

### 4.3 增益档是附加，不是前提

读图（导出 PNG + 逐条观察）是**增益档**：有它更好，**没有它不得拒绝出分**。

- 通用档（结构化回读的实测值）**三维分数恒须产出**（`references/visual-critic.md` §1.6 分档表）；
- 增益档观察必须**具体可回放**，且**不得替代**通用档。

## 5. 逐阶段闸门命令表（可直接复制）

`<run>` = 本次构建的产物目录。设成你自己的路径即可；下列命令任意 cwd 可跑（脚本自定位）。

```bash
# ── 前置：先定档（§1） ─────────────────────────────────────────
node tools/runtime-check.mjs

# ── L0 安装契约（换机器 / 首次跑之前） ──────────────────────────
node tools/qa-install.mjs

# ── L1 → L2：Design System 出口 ───────────────────────────────
node tools/qa-l2.mjs       --spec <run>/dsspec.json --brief <run>/brief.json
node tools/contrast-audit.mjs    <run>/dsspec.json

# ── L3：发计划之前（H2 的全部） ────────────────────────────────
node tools/precheck.mjs <run>/build-plan.json            # 离线；非 FULL_MODE 时到此为止（§3.4）
node tools/precheck.mjs <run>/build-plan.json --live     # FULL_MODE 才有意义（§3.3）

# ── L4：Visual Critic 出口（H3 的全部） ────────────────────────
node tools/qa-critic.mjs --report <run>/critic-report.json \
                         --brief  <run>/brief.json \
                         --spec   <run>/dsspec.json

# ── L5：出口闸门 ──────────────────────────────────────────────
node tools/qa-export.mjs --manifest <run>/export-manifest.json

# ── 全局（H2 时刻一）：文档引用 ────────────────────────────────
node tools/check-refs.mjs
```

**用户产物的档位与仓库自带的 few-shot 不同**：自带样例走 `--strict`（等于给「样例自身必须干净」装了门禁），
用户产物用默认档（`WARN` 不阻塞，但必须在记录表里抄下来）。`qa-install.mjs` 的行为段跑不起来时记
`装置缺口`，不算产品缺陷。

## 7. 不通过怎么算

**D1 通过** = H1 / H2 / H3 **三条全部通过**，且**每一条都有工具输出原文可引**。

不通过时按三档归因，**归因决定下一步动作**：

| 归因 | 含义 | 动作 |
|---|---|---|
| **结构错误 / 契约错误** | 真错误，离线即可判定为真 | 修**产物**（改 Brief / Spec / 计划），不是改校验器 |
| **装置缺口** | 桩没覆盖到的宿主 API，**不算产品缺陷** | 记入本次盲区，提示补桩；不计入 H1/H2/H3 的失败 |
| **未核对** | 档位不足，没证据（典型：无图环境下的画布 id） | 如实记录；**不得**折算为通过或失败 |

另外两类边界，本仓库已有明文，不要重新发明：

- **软判据命中**（`WARN`）：记录，不阻塞；`--strict` 下才致命。软规则同样要有变异测试断言「命中数非零」，
  否则分不清「没有问题」与「规则从未生效」。
- **同名两物**：`assets/examples/example-health`（核心示例，美业「AI 型衣」）与导出包副本是**语义不同的两份数据**，上游即如此。**1.2 收尾已按 lesson #44 交人决策并闭环**：采用最窄的一种 —— 只给导出包副本改名（清单改为 `assets/examples/export/example-healthcare-export.json`，随包文件前缀由 health- 统一改为 healthcare-），核心示例保持不动。不属 D1 的判据范围。

## 8. 本文自身如何避免「人工勾选」

这份标准如果不给出可执行的东西，它自己就是一张人工勾选表——正是 1.1 的病根。三点自查：

1. **每条判据都指向已存在的脚本与已编号的断言**（`qa-l2` QA2 / `qa-export` QA5·QA8·QA9 / `qa-critic` QA3·QA4·QA6·QA7·QA8），
   没有为 D1 新造概念。D1 是**编排**既有闸门，不是新增能力（守 `1.2-plan.md` §8 的红线）。
   断言编号的权威源是**各工具的头部注释**（`CHANGELOG.md` 同步）——若某工具调整了编号，以工具为准并回改本文。
   **这处引用没有机械守卫**：`check-refs.mjs` 只管文件路径，不管符号名，所以「QA7 指的是哪一条」它查不出来。
   这是本文已知的脆弱点，靠改工具时同步（改动校验器的人本来就要改它的头部注释）。

### 8.1 D2 运行 A 的结案（2026-09-17 回写）

**判据命中**：运行 A **漏跑 3 条**（`precheck --live` / `layout-audit` / `check-refs`），
按事先定好的「出现任一次漏跑即立项」——**立项成立**。

**但立项范围要改，理由必须一并写下来**：漏跑的原因**不是**「命令多到记不住」，
而是**「不知道该在什么时候跑它们」**。三条各自的具体形态：

| 漏跑的命令 | 真实原因 | 性质 |
|---|---|---|
| `precheck --live` | 本轮按超时分段构建（14 批），没有「一张完整计划」这种提交物，该命令缺少概念上的输入对象 | **接入点缺失** |
| `layout-audit` | 它要的 readback 形状（带几何的树）与 Bridge 实际返回对不上——`get-node depth≥2` 会剥掉几何字段，想拿几何必须逐节点单读 | **接口不匹配** |
| `check-refs` | 纯文档闸门，与构建流程无耦合，跑它的时机在流程上没有锚点 | **无触发时机** |

**所以结论不是「做一个跑完 10 条命令的编排器」，而是「先把这三条命令的接入点修好」**：

1. `layout-audit` 直接吃 `get-node` 的原生输出（内部自己处理几何缺失），
   或提供 `--fetch` 模式让它自己按需逐节点拉几何。
2. `precheck --live` 支持**增量计划**（`--plan-part`），使分段构建也能逐段核对引用。
3. `check-refs` 挂到构建收尾的固定动作上（例如与 `qa-export` 同批跑），给它一个时机锚点。

**此项归入 1.3**，作为独立交付项，**不进 1.2 范围**（守 §8 净范围不膨胀）。
在接入点修好之前，**「一次性出口检查」不立项**——先做编排器只会把三条接不上的命令
更牢固地封装成一个「看起来全跑了」的假象。

> 说明这是结构性接入点问题（按上表处置）；若漏跑的是**另外几条**，
> 则更可能是「命令表本身就太长」——那时才轮到考虑编排器。

#### 对 §2.1 判据的复核：`layout-audit` 的假阳性是**判据级**缺陷，不只是接口问题

本轮最值得写进验收标准的一件事：**该闸门 21 条告警里 20 条是假阳性，而真缺陷它一条都没报出。**

两个方向都错，且都能定位到具体判据：

| 判据 | 本轮表现 | 根因（写在 §2 盲区里，因为它是**验收标准的盲区**而不只是工具的 bug） |
|---|---|---|
| `spacing` | 17 条假阳性 | 对**二维网格**做**单轴排序**判相邻，报出的「间距」实为行距/列距。隐含前提「列表是一维的」从未写出 |
| `spacing` | 3+4 条假阳性 | 图表刻度 / 网格线的间隔由「绘图区 ÷ 刻度数」**算**出，不是从档位**挑**的。隐含前提「间距都在设计档位上」从未写出 |
| `spacing` / `overflow` | **漏报兄弟重叠** | `spacing` 对 `gap < -TOL` 直接跳过并注释「另由 overflow 反映」，而 `overflow` 只管子节点逃出**父级**——**兄弟 vs 兄弟的缝两边都不管** |
| `alignment` | 静默跳过 | 要求跨轴长度相等（`<= TOL`），27 高 vs 21 高的行配对被跳过，**不报也不计入** |
| 全部 | **漏报语义性缺失** | 168 格热力图无任何轴标，几何完全合法，**数值审计在原理上不可见** |

**收编后的复核结论（2026-09-17 补）**

上表四类假阳性中，**前两类已修**（`localSameSpace` + `bandByCross`/`isDataDrivenSpacing`），
`spacing` 由 **21 条降到 1 条**，且余下那条经复核属**保留上报**（两端对齐的极端留白，见下）。
`layout-audit` 另新增 `overlap` / `duplicate` 两个检查，在真实数据上**抓出 5 条真缺陷**。
`alignment` 的静默跳过**仍未修**（守卫覆盖表标 ❌ 无守卫）。

**收编时新增查出的一条更基础的问题：闸门参数与规格不同源。**
从留存的旧报告 `.vibe/d2-run-b/layout-audit.json` 的 `scales` 里读出：

```json
{"font":[14,16,20,22,26], "minTouch":0, "baseline":null}
```

- `minTouch: 0` ⇒ **触控检查上一轮没在跑**（`side < 0` 恒假）。旧报告「touch 0 条」不是"合格"。
- `baseline: null` ⇒ **页框基准检查上一轮也没跑**。
- `font` 含 **16** ⇒ L2 声明的是 14/20/22/26，**含 16 等于把标准放宽到能放过 16px 的系统性偏差**；
  本轮用真字阶重查，立刻报出 18 处。

> ⇒ **「闸门全绿」是在三条检查缺席或放宽的情况下取得的。**
> 这一条比任何单条缺陷都更该进验收标准：**校验器的档位参数必须来自 L2 Spec 原文，
> 不能跟着构建脚本里"顺手写的"一份走**；且**校验器必须能自证「这轮我有机会报错吗」**。
> 四个留痕段（`unchecked`/`skipped`/`dataDrivenSpacing`/`inputCoverage`）即为此而加。

**这对 §2 的意义**：§2.4「已知盲区」原先写的是「只能观测到算得出/指得出源，无法证明没被手工编辑」，
该条仍成立；但本轮暴露出**盲区不止这一类**，还有三类必须一并写明：

- **① 数值审计对「语义性缺失」原理性失明** —— 无轴标 / 无单位 / 无空态提示 / 无图例，
  全部是几何合法的。**这类只能靠「产物是否可读」这层判据，且目前它没有机械裁判**（见下条）。
  **收编后仍存在 —— 这是判定的能力边界，不是实现缺口，补不了。**
- **② 判据的隐含前提不成立时会产出假阳性，而假阳性会稀释真信号** —— 21 条噪音里藏 0 条真缺陷，
  一个只看汇总行（`{"total":21}`）的人会得出「有 21 个问题」的**反向结论**。
  **故「闸门绿」与「闸门红」都不可单独采信**：红要逐条复算，绿要有「这轮它有机会报错吗」的反问。
- **③（收编时新增）「没查」与「查了没问题」在产物里可能长得一模一样** —— 旧版工具连
  `unchecked` 字段都没有，关掉检查后报 0 与通过后报 0 **在产物上不可区分**。
  这不是"人看漏了"，是**工具没给人看的可能**。
  ⇒ **每个校验器都必须能回答「这轮哪些项没查、为什么」**，且答案要落在产物里，不能落在人的记忆里。

**这也是 §4.3 那条纪律的第二次验证**：运行 A 已证「读图是增益、不是前提」，
本轮证的是它的**反面**——**只有读图能发现的那 3 条缺陷，恰好是 `layout-audit` 结构性看不见的**。
两轮合起来给出的结论是：**通用档（结构化）与增益档（读图）不是冗余，是互补**，
C2 §1.6 的两档制设计因此得到实测支持，**不需要修改**。

#### 大屏基线问题 —— 已裁决（2026-09-17 用户授权代为判定）

用户选定画布 **3840×2160**，而规则库把**大屏设计基准定义为 1920×1080**。
经查两处权威定义**完全一致**、无歧义：

- `assets/style-library/gov-digital-screen.json` → `geometry.frame`：「1920x1080 基准（3840x2160 出 2x）」
- `references/design-style-library.md` §C：「基准 1920×1080，按 3840×2160 出 2x」

三条独立理由支持**以 1920×1080 为设计基准、3840×2160 为 @2x 出图倍率**：

1. **出图倍率与设计尺寸是两层概念**。类似 iOS 的 `@2x/@3x` 与 CSS 的 `devicePixelRatio`——
   设计师在 375pt 上排布、系统按 3x 渲染，**没人会把 1125px 当设计基准**。大屏同理。
   `frameBaseline` 这个字段名本身就指的是**设计基准**，Schema 描述里
   「如 1440x900 / 375x812 / 1920x1080(@2x 3840x2160)」也是这个写法。
2. **规则库自身的所有大屏数值都是按 1920 定的，按 3840 会自相矛盾**。
   `TitleBar 高度占比 8%`（=86px，`GEO-1` 明写「1080×8% ≈ 86」）；
   正文 ≥14px 的依据是「3–10 米观看距离」——这个下限是**逻辑像素语义**。
   若基准变 3840，则 86px 的顶栏与 14px 的正文全都不成立，**必须整体重推**，
   而规则库从没这么定义过。
3. **按 3840 重推会背离「数据即装饰、密集可读」的设计意图**。14px 翻倍成 28px 后，
   3–10 米外看字大得离谱，一屏塞不下本该有的信息密度——与 preset 声明的 `dense`、
   「图表占比 ≥50%」直接冲突。**倍率方案则视觉大小不变、只是像素更密**，正是 4K 屏要的效果。

**结论**：本轮记录 `frameBaseline: "1920x1080（大屏设计基准；出图 3840x2160 @2x）"` **正确，无需改动 L2**。

**唯一的真例外**（已写进 `references/design-system.md` 新增规则 **LD-10**）：
用户若明确要求「**按物理像素 1:1 输出、不做缩放渲染**」（典型是 **LED 拼接屏点对点出图**），
此时才把真实物理分辨率当设计基准，且 **L2 的 `typography` / `spacing` 必须整体按倍率重推**——
那是**一次规则切换**，不是改一个字段。本轮不属于此情形（用户选的是「大屏驾驶舱 3840×2160」，
按行业惯例即出图尺寸）。

> **这项已从「待裁决」改为「已裁决」**，运行 B 的验收结论**不再带生效条件**。

| 最耗时的一项 | 效果类参数不可见（#57） | **插件会话退化态**（#65，12 次，占本轮绝大部分时间） |
| **闸门参数与规格是否同源** | ✅ 同源 | **⚠️ 否**（`minTouch:0` / `baseline:null` / `font` 含 16，**三条检查缺席或放宽**） |

**一个跨两次的观察，补进 §7「不通过怎么算」的语境**：两轮最耗时的翻车点**都发生在「工具报绿」的
地方**——运行 A 是「毛玻璃回读正确、结构校验全绿、导出图却毫无玻璃感」，
运行 B 是「21 条告警里 20 条是噪音、真缺陷一条没报」。

**两次实测因此共同支持一条判据：闸门绿只是必要条件，不是充分条件；
每轮至少要有一次「不依赖闸门」的独立复核（运行 A 是像素 A/B 对照，运行 B 是读图）。**

**运行 B 的收编又给这条判据加了一句**（第三次实测的补充）：
「闸门绿」还有一个更前置的坑 —— **闸门可能根本没在跑，或跑的参数不是规格里的那套**。
所以完整的判据应该是三层：
1. **闸门跑了吗**（`unchecked` / `inputCoverage` 能自证）
2. **闸门用对参数了吗**（档位来自 L2 Spec 原文，不是构建脚本里顺手写的）
3. **闸门有能力看见吗**（语义性缺失类缺陷，数值审计原理上做不到）

前两层本轮已机械化（四个留痕段 + 参数同源纪律）；**第三层无机械裁判，仍需读图**。
这条已记入 `1.2-plan.md` §2.1 主线判断的验证证据链。
